# Protokit design notes

Protokit is planned to generate integration between Protocol Buffers messages
and Dogma. These notes record agreed behavior and open questions; implementation
is not published in this repository. The first implementation targets Go.
TypeScript is deferred, while annotations should remain suitable for equivalent
behavior in other languages.

## Agreed initial Go features

Each annotated type declares one role. Commands, events, and deadlines also
supply a stable UUID and register automatically during package initialization.
Aggregate and process roots do not enter the message registry.

Binary serialization is generated by default, using the standard Protobuf
runtime. A boolean option disables it for handwritten methods or another
serialization generator. Helper-only generation remains a future design item.

Validation generation uses an optional boolean with three states:

- Unset generates an adapter only when the annotated message, its own fields,
  or its oneof groups carry Protovalidate options.
- True explicitly generates the adapter.
- False leaves validation handwritten.

Rules inside referenced types do not establish that the author considered
validation for the enclosing Dogma message. They do not trigger generation.
Removing the final direct rule removes the adapter when the override is unset.
The missing method then becomes visible when Go checks the Dogma interface.

## Description templates

Description templates are deferred. They describe a single line for activity
logs, not a large document. The intended feature set includes nested field
substitution, presence checks, comparisons, boolean flags, and if/else branches.
Loops, arbitrary function calls, and embedded application code are excluded. The
template syntax and cross-language formatting rules remain undecided.

Templates should be checked during generation and compiled into native code,
without a template runtime dependency. Unknown paths fail generation. Presence
checks require explicit Protobuf presence; fields with implicit presence require
value comparisons. A process description may need access to the ended flag.

More complex behavior is handwritten in each language. Translating handwritten
Go into TypeScript, or running it through WebAssembly, is outside this design.
Richer descriptions for agents require a separate Dogma API discussion first.
Schema documentation is another deferred topic.

## Snapshot versions and validation context

Snapshot versioning is deferred until the root validation contracts are settled.
A snapshot can decode successfully while representing state that current
application logic would not produce. Changes to ApplyEvent can cause this even
without a schema change.

The latest proposed behavior uses an explicit-presence version field with an
annotated current value. MarshalBinary stamps the current value into the output
when the field is absent, preserving any explicitly present version.
Unmarshaling preserves stored data. Scoped root validation determines when
version compatibility is required and can reject an aggregate snapshot for event
replay. Serialization should not mutate the caller's object.

Historical data with no version needs further design: re-encoding an absent
version would stamp it as current. Persisted process state also needs separate
recovery semantics because it cannot be rebuilt from event history.

Explore version-change use cases later to provide application guidance, then
identify what tooling can automate. Schema changes alone do not capture every
semantic compatibility change. See [Dogma issue 226] and [Primo issue 78].

Contextual validation remains open for messages too. New values may have
stricter rules than historical ones. Investigate whether Protovalidate and CEL
can consume this distinction, including inside reusable value objects without
making those objects depend on Dogma scopes.

## Generator cooperation and future languages

Primo remains independent of Dogma. An explicit binary-generation opt-out is
planned for the initial implementation. Future options include removing
marshaling from Primo or a generic feature-ownership convention understood by
cooperating generators. One possible convention annotates extension declarations
with feature claims that Primo can inspect without recognizing Dogma options.
This declares ownership but cannot prove that another plugin actually ran.
Changing Dogma's method names or introducing runtime fallback method sets is
less attractive than resolving ownership during generation.

The TypeScript prototype uses protobuf-es v2 plain objects with schema
descriptors. A registry associates description and validation callbacks with
message names, schemas, roles, and UUIDs. Generated registration could establish
those bindings, with a language-specific mechanism for handwritten callbacks.
The prototype is unofficial and does not define the final TypeScript contract.

One protoc plugin can emit files for multiple languages. Language-specific
emitters could share option parsing and semantics, but the eventual packaging
choice remains open.
